### 3-B. 상태박스 계약 (10판 — 결과 카드형)

상태박스는 **최대 2장의 결과 카드**다(위 = 현재군 카드, 아래 = 과거군 카드).
카드 시각은 팝업 목록 카드와 **같은 언어**(`popup.tsx`의 `CARD_STYLE` 재사용 — 실물은 `background:
rgba(255,255,255,0.05); borderRadius:4px; padding:8px 10px; marginBottom:4px`(popup.tsx:144-149),
여기에 `fontSize:12px`·내부 줄 `gap:6px`).
**카드 간격의 문은 하나다(10판)**: 상태박스 컨테이너가 `display:flex; flexDirection:column; gap:"8px"`로
군 간 8px를 소유하고, 카드에는 `marginBottom:0`을 **CARD_STYLE 뒤에** 병합해 목록용 4px 간격을 덮는다
(간격 값이 두 곳에 살면 한쪽만 고치는 날 군 간격이 12px로 어긋난다).
9판까지의 외곽 테두리 박스(`border:1px solid rgba(255,255,255,0.15)`)는 폐기한다. 내용 0줄인 카드는
미렌더, 두 카드 모두 0줄이면 상태박스 전체 미렌더(승계).

**[현재군 카드]** — 슬롯 ⓪~④의 조건·키·색 계약은 9판과 **바이트 동일**(무변경 승계 — 아래 표가 그
승계분이다). 각 슬롯은 **전폭 블록 줄**이고, ③ 실패의 수신 시각은 문장 뒤 인라인 텍스트다
(flex 아님 — 감김 붕괴 원리적 불가).

| 슬롯 | 조건 | 문구 | 색 |
|---|---|---|---|
| ⓪ 로딩 | `overview===null && !failure` | `LOADING` | 회색 `#9aa0a6` |
| ① 진행 | busy | 미리보기 왕복(무토큰 1차) 중 `APPLY_PREVIEWING`("확인 중…") / 토큰 재호출(실행) 중 `APPLYING`("적용 중…") — D14 분기, `runApplyAll`의 token 유무로 판정 | 회색 |

| ③ 실패 | `lastFailure` | `tCode` 단일 관문 + 수신 시각 | 주황 `#ffb454` |

> **⚠️ 12판 — ④ 시작 안내 슬롯 폐기**: 9~11판의 ④(`NO_PROFILES_YET`)는 삭제한다. 그 안내가 하던 일(저장 위치 알리기)을 §3-D의 설명 줄이 겸하게 되어 **같은 사실을 두 자리에서 말하던 상태**가 해소됐고, 안내가 *"일어난 일을 말하는 자리"*(상태박스)에 있던 구조적 어긋남도 함께 사라진다.
>
> **미렌더 조건은 승계된 그대로다 — 프로필 수가 조건이 아니다**: 상태박스는 **현재군 카드와 과거군 카드의 줄이 모두 0일 때만** 그려지지 않는다. ④ 폐기 후 현재군에 남는 슬롯은 **⓪ 로딩 · ① 진행 · ② 실행 중 고지 · ③ 실패** 넷이고, 그중 **② `BULK_RUNNING_NOTE`는 프로필 수와 무관하게 `counts.running > 0`이면 선다**(`index.tsx:695` — `running`은 프로필 유무를 보지 않고, 백엔드도 별도로 센다 `main.py:737`). 과거군(`lastSummary`)도 마찬가지로 프로필 수와 무관하다.
> 따라서 **"프로필이 0이면 상태박스가 사라진다"는 거짓이고, 옳은 문장은 이것이다**:
>
> > 등록 있음·프로필 0 상태에서 **달리 말할 것이 없으면**(로딩 아님 · 진행 아님 · 실행 중 게임 0 · 실패 없음 · 직전 일괄 결과 없음) 상태박스가 통째로 미렌더된다 — ④ 폐기로 *그 상태에서만 서던 줄*이 사라졌기 때문이다. **실행 중인 게임이 있거나 직전 결과가 남아 있으면 상태박스는 그대로 선다**(그 사실들은 ④와 무관하고, 프로필이 없다는 이유로 숨기면 화면이 거짓을 말한다).
>
> **⚠️ 「프로필 0 + 실행 중」은 드문 조합이 아니라 우리가 안내하는 흐름 그 자체다**: §5-B의 저장 안내가 *"게임에서 그래픽 옵션을 맞춘 뒤, 게임을 종료하고 [프로필 저장]을 누르라"*고 말하므로, 사용자가 게임을 켠 채 QAM을 여는 순간이 정확히 이 상태다. 이 조합을 예외로 취급하는 서술·검사는 전부 오류다(§15-B ⑤ 음성 대조군, §16-⑪).
> **잔글씨 정리 효과(5 → 2)도 같은 단서 아래에서만 참이다** — "달리 말할 것이 없는 초기 화면"의 이야기이고, 첫 개방 직후 ⓪ 로딩 줄이 잠깐 서는 것은 별개다.

### 3-C. 현황 카운트

- 표기: **`COUNT_SUMMARY` = "게임 {total}개 등록 · 프로필 저장: {dock} {dock_ready} · {internal} {internal_ready}"**(12판 — 분모를 문장 앞으로).
  - **D03(의미 라벨 부착)은 그대로 유효하고, 신 문구도 라벨을 유지한다** — "프로필 저장:"이 그 라벨이다. D03이 막으려던 것은 *라벨 없는 수*가 "적용 현황"으로 오독되는 것이고, QAM이 "현재 적용"을 원리적으로 모른다는 사실은 12판에서도 변함이 없다. **표기 변경은 D03의 철회가 아니다.**
  - 12판이 고친 것은 **분모의 정체 불명**이다: `3/10`의 `10`이 등록 게임 수라는 사실이 화면 어디에도 없었다. 분모를 앞으로 빼 먼저 정의하면 설명이 불필요해지고, 기호 5 → 3, `/{total}` 반복 소멸로 표시명이 길어져도(F11 상한 20자) 한 줄 여유가 생긴다. "등록 10개"가 아니라 **"게임 10개 등록"**인 이유 = 전자는 무엇이 10개인지 여전히 말하지 않는다.
  - **U-1(§18) 처분과의 관계**: U-1은 "`N/전체` 분수 표기 유지"였고 12판이 이를 **뒤집는다**(사용자 확정, 2026-08-13). 분수를 유지하기로 한 근거(D03 라벨 부착으로 오독 해소)는 *라벨*에 있었지 *분수*에 있지 않았고, 라벨은 신 문구가 그대로 들고 간다.
  - 등록 0에서는 이 줄이 `NO_GAMES`로 갈리므로 "게임 0개 등록"은 뜨지 않는다(아래 D01 조항 불변).
  - 치환자 집합 불변(5종) — `test_i18n_sets` 무영향.
- 산출: `counts.dock_ready`·`internal_ready`·`total` 그대로(프론트 계산 0, 봉투 확장 0).
- **`counts` 미도착(overview===null) 동안 `NO_GAMES`를 그리지 않는다**(D01 — 명문화). 카운트 줄은 로딩 중 같은 높이의 빈 자리로 유지(레이아웃 점프 방지). `total===0` 확정 시에만 `NO_GAMES`("등록된 게임이 없습니다 — [게임 감지]에서 추가할 수 있습니다").

### 3-D. 설명 영역

`HINT_STYLE`. **설명 영역은 어느 상태에서든 한 줄만 그린다 — 상시 줄 + 조건부 줄의 누적 구조를 폐기하고 상태별 교체로 바꾼다**(12판, 사용자 확정 2026-08-13. 11판의 U-5 "①상시 + ②조건부" 구조는 이 절로 대체된다).

**판정표(정본)** — 위에서부터 먼저 참인 행 하나만 그린다:

| # | 조건 | 그리는 것 |
|---|---|---|
| 1 | **`!counts`** — 조회 전(로딩) **및 조회 실패**(실패는 `overview`를 만들지 않는다: `index.tsx`의 `onLoadFail`/`onCallFail`이 `setFailure`만 한다) **및 실패 승계 재개방** | **없음** (D01 — 모르는 상태에서 단언하지 않는다) |
| 2 | `counts.total === 0` | **없음** — 그 상태의 안내는 카운트 줄 `NO_GAMES`가 전담한다([게임 감지]를 가리키는 손가락을 하나로 유지, §16-⑧ 처분) |
| 3 | `counts.total > 0 && counts.dock_ready + counts.internal_ready === 0` | **`QAM_ABOUT_GUIDE`** = "[게임별 적용/저장]에서 게임별 그래픽 설정을 저장할 수 있습니다." |
| 4 | 그 외(프로필 1개 이상) | **`QAM_ABOUT`** = "프로필 적용 버튼은 해당 프로필이 저장된 게임만 대상으로 합니다." |

- **1행은 한 조건이 여러 화면 상태를 덮는다**(로딩 · 조회 실패 · 실패 승계 재개방). 검사도 그 전부를 장면으로 들어야 한다(§15-B ⑤) — "장면 하나"로 줄이면 조회 실패에서 설명 줄이 되살아나도 초록불이다.
- **자리(placeholder)를 잡지 않는다**(세션 처분, 2026-08-13): 카운트 줄은 `minHeight:16px`로 자리를 지키지만(레이아웃 점프 방지), 설명 줄은 **1·2행에서 영구히 없는 줄**이라 자리를 잡으면 등록 0 화면에 빈 칸이 상주해 "말할 게 없으면 그리지 않는다"와 어긋난다. 도착 시 1줄 밀림은 상태박스 로딩 줄이 사라지는 움직임과 같은 크기라 새 소음이 아니다.
- **3행의 조건식은 11판 `noProfilesYet`과 바이트 동일하다.** 11판에서 이 식은 §3-B ④와 §3-D ②가 **공유**하던 것이고, ④가 폐기되면서 소비자가 이 한 곳으로 줄었다 — "조건이 한 곳이어야 두 줄이 함께 사라진다"는 규율은 **소비자가 하나가 되어 구조적으로 달성**됐다(3행과 4행은 **같은 식의 참/거짓**이지 별개 식이 아니다 — 신설 조건 금지 규율 유지).
- **`QAM_ABOUT`의 값이 하는 일**: 사용자가 버튼 괄호 `(3개)`와 카운트 줄 "게임 10개 등록"의 차이를 해석하지 못해 *"10개 전부 바뀐다"* 또는 *"7개가 누락됐다"*로 오해하던 자리를 메운다. **"적용합니다"가 아니라 "대상으로 합니다"인 이유**: 실행 중인 게임은 대상이면서도 거부되므로 "적용한다"는 단언이 거짓이 될 수 있다.
- **구현 규약(검사 가능성)**: 키를 변수로 넘기지 않는다 — `t("QAM_ABOUT_GUIDE")`·`t("QAM_ABOUT")` **리터럴 두 갈래**로 쓴다(§10-B′의 "참조 0 키 grep" 규율과 `i18n_jsx_scan`이 리터럴을 보므로, 변수 경유는 두 키를 고아로 오판하게 만든다).
- **A5**: `QAM_ABOUT_GUIDE`의 "그래픽 설정"은 게임 원본 설정을 가리키므로 허용 범위(소유자 명시 어구). `QAM_ABOUT`에는 "설정"이 없다.
- **치환자 소멸**: 신 `QAM_ABOUT_GUIDE`는 ko/en 모두 치환자 0개다(11판 값의 `{dock}`·`{internal}` 소멸). **ko/en이 함께 잃으므로 비대칭이 아니다**(`test_i18n_sets` 무저촉). 단 **호출부의 죽은 인자를 함께 지운다** — `index.tsx:839`의 `{ dock: …, internal: … }` 제거(안 지우면 다음 개정이 치환자 있는 줄로 오독한다).
- 기각 유지(재제안 금지): **정의문**("프로필은 …입니다" — 앱이 가르치려 드는 인상) / **기기 사용 방식·시점 전제**("연결하거나 분리한 뒤"류 — 사용 방식은 사용자마다 다르다. 단 **앱 사용법 안내는 허용**) / **조건부 사실의 상시 단언** / "프로필로 저장할 수 있습니다"(한 화면에 「프로필」이 이미 8회).
- 진입 안내는 6~8행 description이 분담(M10) — 불변.

## 4. 팝업 공통 기반

### 4-A. 골격

새 파일 `src/popup.tsx`:

```tsx
function GfxPopup({ title, icon, onCancel, children, closeModal }) {
  return (
    <ModalRoot closeModal={closeModal} onCancel={onCancel}>
      <DialogHeader>{icon} {title}</DialogHeader>
      <DialogBody>
        <ErrorBoundary where={...}>{children}</ErrorBoundary>   {/* ★ 경계는 ModalRoot 안쪽 */}
      </DialogBody>
    </ModalRoot>
  );
}
```

- **ErrorBoundary는 DialogBody 안쪽**이다(R-4). `showModal`은 **최상위 엘리먼트에만** `closeModal`을 주입하므로(`index.tsx:141-143`·`ManageTab.tsx:53-54` — 프로젝트가 계약으로 문서화한 사실) 최상위를 ErrorBoundary로 감싸면 주입이 삼켜져 닫기 배선이 죽는다. 한계: **ModalRoot 자체 렌더 실패는 이 경계가 못 가둔다** — 그 실패는 showModal try/catch(§3-A)가 실패 고지로 받는다.
- `DialogHeader`/`DialogBody` 신규 채택(§13). **크기 무지정**(A10) — `popupWidth`/`popupHeight`/`bAllowFullSize` 금지.
- 제목: G "게임별 적용/저장" · D "게임 감지" · S "설정".

### 4-B. 내부 뷰 상태

```ts
type GView = { kind: "list" } | { kind: "detail"; appid: string } | { kind: "backups"; appid: string };
type DView = { kind: "main" } | { kind: "excluded" };
```

- 전환은 명시적 setView(깊이 최대 2 — 뒤로가기 대상이 정적: `backups`→`detail`, `detail`→`list`, `excluded`→`main`).
- **뒤로가기 버튼 `[← 뒤로]`**: 비목록 뷰의 DialogBody 최상단 첫 요소(진입 직후 B 대체 수단·스크롤 밖 밀림 방지).
- **★목록 뷰는 리마운트하지 않는다**(GP#3 — 초판의 `key={view.kind}` 전면 리마운트 폐기): `key`는 상세·백업·제외 뷰에만 적용(그 뷰들의 스크롤 초기화는 유지). 목록 복귀 시 **마지막으로 조작한 행(appid)을 팝업 상태로 기억해 그 행에 동적 `preferredFocus`**(§4-E)를 준다 — Steam 포커스 엔진이 포커스를 따라 스크롤하므로 위치가 복원된다(포커스 추종은 §16-⑥ 실기 확인). 등록 해제 후 복귀는 인접 행(다음 항목, 없으면 이전)으로.

### 4-C. 확인 게이트 — 중첩 1안 + 내부 뷰 폴백 [핵심 구조]

**요구(A10)**: 중첩(lsfg dist:1647 선례)과 내부 뷰 전환을 코드 구조 변경 없이 전환 가능해야 한다.
**개정 2판**: 입력형 확인창 2종(type-to-confirm·이름 편집)이 표현 가능하도록 spec을 확장(R-1 — 초판의 정적 `okDisabled`·무인자 `onOK`로는 구현 불능이었다).

```ts
// popup.tsx — ★ 입력형/비입력형 discriminated union (Codex N-03: `onOK(inputValue?: string)` 단일형은
//   strict 빌드에서 `string | undefined`가 `runRename(name: string)` 등 실물 시그니처와 충돌한다)
interface ConfirmSpecBase {
  title: string;
  body: ReactNode;                    // 기존 확인창들의 strDescription 내용물 그대로
  warnBlock?: ReactNode;              // ⚠ 강조 블록(전체 초기화 전용, §7)
  okText: string;
  cancelText?: string;                // 기본 t("CANCEL")
}
export interface PlainConfirmSpec extends ConfirmSpecBase {
  kind: "plain";
  onOK: () => void;
}
export interface InputConfirmSpec extends ConfirmSpecBase {
  kind: "input";
  /** 렌더러가 TextField와 그 상태를 소유한다. */
  input: { label: string; initial: string };
  /** 입력값에서 파생하는 동적 비활성. 미지정 = OK 항상 활성. */
  okDisabled?: (value: string) => boolean;
  onOK: (value: string) => void;      // ★ string 확정 — undefined 없음
  /** 렌더러가 언마운트 직전 마지막 입력값을 알린다 — 호출부가 보존·재공급(§7 입력 보존). */
  onInputSnapshot?: (value: string) => void;
}
export type ConfirmSpec = PlainConfirmSpec | InputConfirmSpec;
export const NESTED_CONFIRM = true;   // 실기 실패 시 false 한 줄 — 폴백 전환 스위치

function useConfirmGate(setOverlay) {
  return (spec: ConfirmSpec, failKey: StringKey, onFail: (msg: string) => void) => {
    if (NESTED_CONFIRM) {
      try { showModal(<SpecConfirmModal spec={spec} />); }
      catch (e) { console.error("[gfxprofile] confirm gate failed", e); onFail(t(failKey)); }
    } else {
      setOverlay(spec);               // 팝업 내부 오버레이로 렌더
    }
  };
}
```

- **두 렌더러, 한 spec**: `SpecConfirmModal`은 `spec.kind`로 분기해 — `"plain"`이면 `ConfirmModal(strTitle/strDescription=<>{warnBlock}{body}</>/strOKButtonText/onOK={spec.onOK})`, `"input"`이면 body 뒤에 `<TextField label value focusOnMount onChange/>`를 붙이고 `bOKDisabled={spec.okDisabled?.(value) ?? false}` / `onOK={() => spec.onOK(value)}` — **타입 내로잉으로 strict 빌드 성립**(N-03). **입력 state(useState)는 렌더러 내부**에 있고 `okDisabled(value)`를 매 입력마다 재평가한다(현행 `ResetConfirm` 배선과 동형 — `ManageTab.tsx:120-155`). 폴백 오버레이 렌더러도 같은 분기·같은 요소를 그린다.
- **실패 키는 게이트 인자**(R-1 부수 지적 해소) — 호출부가 문구를 준다(공유 문장이 어느 경로에선 거짓이 되는 사고의 재발 방지, `ManageTab.tsx:534-542` 교훈 그대로).
- **기존 확인창의 spec화**: `makeSaveConfirmSpec`·`makeDeleteConfirmSpec`(§9 보강판)·`makeRestoreConfirmSpec`·`makeRestoreFollowUpSpec`·`makeDiscoverWarnSpec`(`kind:"plain"` — `onOK()`), `makeResetConfirmSpec`(`kind:"input"` — `input:{label: RESET_CONFIRM_FIELD_LABEL, initial: 보존값}`, `okDisabled: v => v !== params.challenge`, `onOK: (v: string) => runReset(token, v)`), `makeNameEditSpec`(`kind:"input"` — `okDisabled` 미지정=OK 항상 활성(빈 값=기본 복귀), `onOK: (v: string) => runRename(profile, v)` — string 확정이라 `runRename(name: string)` 실물 시그니처와 정합). 문구·정보량은 현행 유지가 원칙, 변경분은 §9·§7·§5-C 명시분뿐.
- **입력값 보존**(GP#9): 호출부(팝업 S)가 `onInputSnapshot`으로 마지막 입력을 상태에 담고, TOCTOU 재질문·재오픈 시 `initial`로 되돌려준다 — 가상 키보드로 30입력쯤 찍은 값이 B 오조작 한 번에 소실되지 않는다.

**★소비자 계약 개정 4항 [8판 확정 — P15-A 설계 판단, 구현 완료]**: 위 서술은 "언제 다시 읽는가"만 정했고 **누가 그 규칙을 들고 있는가**를 정하지 않아, 팝업마다 방어 코드가 갈라지는 자리를 남겼다(이월 대장 #3·#4 — 조회 잠금 후퇴·`DELETE_FAILED` 비대칭). 규칙은 **문 하나**로 모은다:

1. **세대 가드** — 재조회마다 세대 카운터를 올리고 **최신 세대의 응답만** 반영한다(옛 응답은 없던 일). 역순 도착으로 화면이 되감기는 갈래가 원천 소멸한다.
2. **busy 통합** — 조회도 변이와 같은 문에서 busy를 켠다(진행 **수** 카운터 — 겹침이 실재하므로 불리언이 아니다). [다시 검색] 연타 잠금이 조회 경로에서도 성립한다.
3. **실패 후 재조회 = 호출 유형 기준** — 미리보기·토큰 발급(무쓰기 보장)은 재조회 0 / **확정 실행(토큰 소비)은 성공·실패 무관 재조회 + `onMutate()`**. 엔진은 쓴 **뒤에** 거부할 수 있어(§5-E) 실패 봉투 뒤의 화면이 낡는다. ⚠️ 이 규칙 때문에 `onMutate`는 **거부·실패에도 발화**한다 — 수신 측(QAM) 갱신 핸들러는 **멱등**이어야 한다.
4. **note 즉시 표시** — 데이터 정합은 1이 보장하므로 note를 재조회 완료까지 미루지 않는다. 재조회가 실패하면 note를 덮지 않고 **보조 줄**로 "다시 읽지 못했다"를 병기한다(P15-E R4).

**구현 실물**: 규칙은 `popup.tsx`의 `useDataDoor`(문) — `usePopupData`(팝업 3종)와 **QAM이 직접** 쓰는 **두 소비자**가 상속한다. QAM을 문 밖에 두었던 것이 P15-E 치명 결함(실패 봉투 침묵·카운트 역행)의 뿌리였다 — **"팝업 계약"이 아니라 "데이터를 읽는 모든 화면의 계약"이다.**

### 4-G. 버튼 폭 규약 (10판 신설 — D1)

**사실**: Steam 본체 CSS는 `button.DialogButton { width:100% }`를 전역 적용한다. 이것은 블록 부모만이
아니라 flex 자식에도 발현한다(`flex-basis:auto`가 width를 읽는다) — 인라인 `width`를 명시하지 않은
모든 DialogButton은 팝업 본문 폭(≈604.7px)으로 늘어난다. 미니 프로브는 이 계열을 **원리적으로 못
잡는다**(Steam 스타일시트가 프로브에 없다) — 판정은 실기 CDP 스타일 조회 또는 스샷뿐이다.

**규약**:
1. **팝업 층의 모든 버튼은 `popup.tsx`의 래퍼 `PopupButton` 하나로만 그린다.** 래퍼는 `DialogButton`에
   `width: "fit-content"`를 **호출부 style보다 나중에** 병합해 전역 오염을 차단한다(호출부는 width를
   지정하지 않는다 — minWidth·flex·padding·색만). props는 전부 투과(preferredFocus·disabled 등).
   ```tsx
   // popup.tsx — 확정형(2판, 반증 실측 반영. 이 형태에서 벗어나지 말 것)
   export function PopupButton({ style, children, ...props }: ComponentProps<typeof DialogButton>) {
     return <DialogButton {...props} style={{ ...style, width: "fit-content" }}>{children}</DialogButton>;
   }
   ```
   - 타입은 **`ComponentProps<typeof DialogButton>`**이다 — `DialogButtonProps`를 `@decky/ui`에서
     직접 import하면 **build.sh grep ①(단일 관문) 위반**이고 `deckyui.ts`는 그 타입을 재수출하지
     않는다(실측).
   - **children은 구조분해해 JSX 자식으로 전달한다** — `{...props}`에 children을 남겨 prop으로
     넘기면 `probe_kit.cjs`가 children **prop**을 스킵하고(:172) JSX 자리 children에서만 라벨을
     읽어(:208) 전 버튼 라벨이 ""가 된다 — 회귀 4종 파괴(test_games_popup 크래시 포함) 실측.
     JSX 자식 전달형으로 3종 복구 실측.
   - `ref`는 투과되지 않는다(`ComponentProps`는 RefAttributes 미포함) — 현 호출부에 ref 사용 0이라
     무해. ref가 필요해지는 날 forwardRef로 확장한다(지금 만들지 않는다).
2. **문 하나 강제**: `<DialogButton` JSX의 직접 사용은 `popup.tsx` 한 파일만 허용. 파일 안에서도
   두 자리뿐이다 — ⓐ 래퍼 정의부 ⓑ **폴백 오버레이 확인창의 푸터 2버튼**(예외 사유: Steam
   `ConfirmModal` 푸터의 flex-grow 반폭 열과 시각을 동일하게 유지해야 §4-C "두 렌더러가 같은 것을
   그린다" 계약과 입력면 시각 계약이 자기 정합한다 — fit-content로 접으면 중첩/폴백의 푸터 모양이 갈린다).
   `build.sh` grep ⑤가 파일 단위로 잠근다(`@decky/ui` import 단일 관문 grep과 동형 — build.sh:72-74
   선례). 파일 밖 예외 목록은 두지 않는다.
3. **세로 스택 버튼**(설명 줄을 아래에 거느리는 동작 버튼 — 실물 6곳: 팝업 G 상세 4(ActionButton) ·
   설정 1(`RESET_OPEN`) · 감지 1(`DISCOVER_PICK_FILE`)):
   fit-content(1항 자동) + flex 부모에서는 `alignSelf:"flex-start"` + **내용 좌측 정렬**(`textAlign:"left"`,
   런타임에 버튼 내부가 flex로 판명되면 `justifyContent:"flex-start"` — 실기 §16-⑮ ⓓ에서 확인).
   설명 줄(desc)은 버튼의 가로 패딩과 같은 `paddingLeft`(공용 상수 하나)로 **라벨과 정렬 축을 공유**한다
   — 현행의 "버튼 글자 가운데·설명 왼쪽" 축 어긋남 해소.
   **가로 행 버튼은 대상이 아니다**(좌측 정렬·alignSelf를 강제하지 않는다): 이름 바꾸기 2(ROW_STYLE) ·
   [다시 검색]·[모두 추가] 액션 줄 · 목록 행 버튼들 — 이들은 행 안에서 제 폭만 접으면 된다(1항).
4. **§5-A 정합**: 행 버튼의 "minWidth 110px 고정·전 행 x좌표 동일" 계약(GP#2)은 **불변이며 살아 있다**
   — 584.7px로 늘어난 현 상태가 오히려 설계 위반이었다. fit-content에서도 계약이 성립하는 근거:
   행 버튼의 내용(프로필 표시명 + 마커 자리 상시 예약)은 **전 행에서 동일**하므로 폭도 전 행 동일이다.
   minWidth 110은 하한으로 존치. 행 버튼에 별도 maxWidth는 두지 않는다 — 상한의 문은
   표시명 길이 상한(`PROFILE_NAME_MAX`=20, `limits.ts`) 하나다(알려진 한계: 20자 꽉 채운 표시명이면
   두 적용 버튼이 게임 이름을 크게 압박한다 — 병적 사례로 처분, 실기 ⑥ 실측 범위).
5. **적용 제외**: ⓐ QAM의 `ButtonItem`(268px 폭 정상 실측 — QAM에서는 전폭이 옳다)
   ⓑ 확인창 2종의 푸터 버튼(ConfirmModal 내부 — DialogTwoColLayout이 flex-grow로 분배, 오염 면역 실측).

- **⚠️ 8판 정오 — 의사코드의 죽은 갈래 3곳**: 위 `except store.RegistryError`(개별 적용·`apply_all` 2곳)와 `apply_all`의 `except engine.Refused`는 **실물에서 도달 불가**다 — `load_registry()`가 `try` 밖에서 먼저 돌고(그 실패는 route 데코레이터가 받는다), 엔진 `apply_all`은 게임별 예외를 내부에서 격리해 `Refused`를 밖으로 내지 않는다. 구현은 **세 갈래를 두지 않았다**(죽은 `except`는 "여기서 그럴 수 있다"는 거짓 주장이 되고, 언젠가 그 거짓을 근거로 코드가 쓰인다). 의사코드는 이 정오와 함께 읽을 것.
- **`_valid_previous`**(D-03): `entry.get("last_applied")`가 `{"dock","internal"}` 밖이면(숫자·임의 문자열·손상 registry) **None으로 접는다** — 봉투 계약 `checked_in: Profile|null` 보존 + 관측기 경로 위생. `load_registry`는 최상위 키만 보정하므로(`store.py:189-194`) 관측기 쪽 검증은 route 층 책임이다. ⚠️ **이 검증은 관측기 입력만 지킨다** — 엔진에는 원 registry가 그대로 들어가므로 raw `last_applied`가 엔진의 `load_meta`/`write_profile` 경로 조각으로 재소비되는 실물 경로(Codex N-02: 절대경로 값이면 `os.path.join` 접두가 버려져 데이터 루트 밖 읽기·쓰기)가 따로 있다 → **엔진 체크인 지점 가드 1줄로 막는다(§14 엔진 변경 제안 — 이 설계의 유일한 엔진 변경)**. 가드 채택으로 관측기(None)와 엔진(체크인 건너뜀)의 판정이 손상 값에서 자연 정합한다.
- **정확성 — 근거와 한계를 정확히**(N-01로 "실패 갈래 전부·동등 정확도" 표현 폐기, 3차 재확인으로 결정화): 체크인이 쓰는 갈래(`engine.py:511-520`)의 `write_profile`은 body→meta 순 별도 atomic write다. **내용 sha 기반 슬롯 지문은 어느 한 파일이라도 내용이 바뀌면 결정적으로 변한다** — ⓐ body+meta 완료 ⓑ body만 완료(부분 쓰기 — 숨김명 body 포함) 모두 관측된다. 체크인 갈래의 전제(디스크 ≠ 직전 프로필 내용)상 body 내용이 반드시 다르고, meta는 `saved_at` 갱신으로 다르다 — "내용 동일 재작성 미검출"이라는 지문 방식의 원리적 한계는 이 경로에서 도달 불가. 체크인 자체 대피(`make_backup`, engine.py:516-518) 실패 = `write_profile` 미도달 = 지문 불변 = null이 정답. 건너뜀/불필요 갈래 = 쓰기 0 = 불변. **잔여 한계(정직 서술)**: 관측은 "슬롯이 바뀌었다"는 사실이지 "체크인이 바꿨다"의 증명이 아니다 — ⓐ 엔진이 관측 창 밖에서 슬롯을 만지는 제3의 경로가 생기면(현행 없음) 오탐 가능 ⓑ 쓰기 비정상 중단의 일시 파일 잔재도 지문을 바꾼다. 둘 다 **과보고(보수적 오탐) 방향**이고, 이 관측의 실패 모드로는 침묵보다 과보고가 안전하다(F6의 본질 = 조용한 덮어쓰기 고지). 간극은 동등성 테스트(ⓒ)가 감시한다.
- **⚠️ 8판 정오 — "잔여 한계는 과보고 방향뿐"은 틀렸다(P11 게이트 R2·C2)**: 침묵 갈래가 **실재했다.** ⓐ 안전 술어를 넓게(`_paths_in_position` — `backups/`까지 요구) 쓰면 백업 폴더만 링크인 정상 게임에서 슬롯 전체가 `"unsafe"`로 접혀 **실제 체크인이 침묵**했다 → **술어를 이 함수가 실제로 읽는 경로(그 슬롯 하나)로 좁혀 회복**했다. ⓑ 남은 갈래 = `profiles/` 루트나 슬롯 **자체**가 데이터 루트 밖 링크인 경우 — 이때도 관측은 침묵한다. **알려진 한계로 처분한다**(P8 R2 전례 = 데이터 루트 안 악의적 심볼릭 링크는 사용자가 확정한 위협 모델 밖 — 그 상태면 직접 `rm`도 가능하다). 제약 안 대안은 전무했다: 링크 너머 읽기 = "루트 밖 읽기 금지" 위반 · 상시 과보고 = 매 적용 거짓 진술 · route 층 선차단 = HANDOFF §8 #11 금지 재판.
- **★손상 registry 「키」의 폐쇄(8판 추가 — P11 워커 ④-2)**: 관측기는 registry의 games **키**를 그대로 도는데 그 키들은 `_VALIDATORS`를 한 번도 지나지 않는다(수동 편집된 `"../../X"`·절대경로 키). 지문을 뜨겠다고 루트 밖을 읽지 않도록, **안전하지 않은 슬롯은 조회 없이 고정 센티널(`"unsafe"`)로 접는다** — `restore.backup_count`·`remove.delete_preview`와 같은 문법이고, 센티널→실물 전이는 과보고 방향이다.
- **엔진 구조 필드안(ⓑ)과의 재심 비교**(D-02·S-03·N-01 — §14에 기록): N-01을 반영해도 ⓐ′(내용 sha 복합 지문)가 부분 쓰기 갈래까지 관측하므로, 엔진 반환·전 raise 지점 다중 수정(ⓑ)의 이득은 **위 잔여 한계(과보고 방향 오탐 가능성)의 제거뿐**이다 — 침묵이 아니라 과보고인 한계를 위해 fence 재계약을 늘릴 이유가 없어 **관측은 ⓐ′ 유지**. (N-02의 경로 오염은 관측 문제가 아니라 쓰기 가드 문제라 별도로 엔진 1줄 가드를 채택 — §14.)
- `apply_all`도 동형: 호출 전 게임별 `(previous, _slot_fp)` 스냅샷(각 게임 `_valid_previous` 통과분만) → 호출 후 대조 → 봉투 `checkin: [{appid, name, profile}]`. 엔진 `apply_all`은 게임별 예외를 내부 격리하므로(row outcome) 봉투가 `ok:true`인 채 실패 게임의 체크인도 이 관측이 덮는다. `save_registry` 실패는 개별 적용과 같은 except 문법으로 `checkin`을 실패 봉투에 부착. 비용 = 직전 프로필이 있는 게임당 슬롯 전 파일 스트리밍 해시 × 전후 2번 — **슬롯 실물 크기에 선형이며 상한은 없다**(실사용 설정 파일은 소형. 결정성이 read 절약보다 우선 — 3·4차 재확인 판정).

  정확히 한 번만 말한다**, 10판):
  1. **⚠ warnBlock**(A8 — 수량·백업 잔존·재등록 전제의 **유일한** 자리):
     > ⚠ 초기화는 등록 기록 {games}개와 플러그인이 인식할 수 있는 프로필 기록 {profiles}개를 삭제 대상으로 삼습니다. 이 수에 포함되지 않은 프로필 데이터도 삭제될 수 있습니다. 백업 폴더는 남지만 프로필 데이터를 옮겨 두는 동안 오래된 백업이 밀려날 수 있습니다. **백업 내용을 되살리려면 게임을 다시 등록한 뒤 복원해 주세요.**

### 8-A. 저장 스키마 [확정 — 초판 유지]

### 8-B. 새 모듈 `py_modules/gfxp/exclude.py` (fence 밖 — confirm/remove/restore 선례) [초판 유지]

**손상 registry 정규화 규칙(Codex D-08 — 신설 봉투 필드 공통)**: 신설 필드는 전부 "raw registry 값"이 아니라 **표시용 정규화 값**이다 —
- `config_path`: str 아니면 `""`(빈 값이면 화면이 줄을 그리지 않는다 — §9 문법).
- `_excluded_rows(reg)`/`exclude.rows(reg)`: `discover_excluded` 값이 dict가 아니면 전체를 `{}`로 접고(§8-B), **개별 항목도 값이 dict가 아니면 그 항목을 결과에서 제외(격리)하고 로그 1줄**을 남긴다. dict인 항목의 `name`이 str 아니면 `"appid {id}"` 폴백, `excluded_at`이 str 아니면 `""`(label도 `""`). 항목 하나의 타입 오류가 route 전체를 죽이지 않는다.
- `counts.excluded`는 격리 후 남은 유효 항목 수가 아니라 **`excluded_map` 원본 키 수**를 쓴다 — 격리된 불량 항목도 "초기화로 지울 것"에는 포함되어야 D-01의 활성 조건이 참을 말한다.

- 토큰 파급(반증 R-14 재확인): 제외 변경은 registry 파일을 바꿔 `reset_fingerprint`(registry sha 포함)를 흔든다 — 미소비 reset/apply_all 토큰 무효화 = 안전 방향. `delete_fingerprint`는 무영향.

### 10-D. 단계 배정 규칙 (R-3 — 구속)

`StringKey = keyof typeof en`(`i18n.ts:17`)이므로 **신설·값 개정 키는 그 키를 참조하는 파일이 생기는 단계(P12~P14)에 en/ko 동반 편입**한다. P15에 남는 것은 **제거 18종(§10-B 정정) + 고아 정리 + 구파일 삭제**뿐이다. `test_i18n_sets`(src 전체 글롭)는 각 단계 종료 시점마다 통과해야 한다.

⚠️ **8판 정오 — §17 P12 완료 기준과의 충돌 해소**(P12 게이트 C6): §17은 P12 완료 기준에 "spec화 전후 **문구 동일성**"을 걸어 두었는데, §9·§7의 문구 **개정분**은 이 규칙(§10-D)에 따라 P13에 편입된다 — 두 조건을 동시에 만족하는 순서는 없다. **해소 = parity-first**: P12의 동일성 검사는 *"옮기는 동안 잃은 것이 없다"*만 재고(구 컴포넌트 ↔ spec 대조), **문구 개정은 참조 단계(P13)에서** 한다. 그래서 P12 시점의 신구 값이 같다는 사실은 검사 통과의 **전제**이지 개정 금지가 아니다. (그 대조 검사 자체는 비교 대상인 구 컴포넌트가 P15에서 삭제되며 예고대로 은퇴했다 — §12 이식 맵.)

### 10-E. 치환자 조사 규칙 (10판 신설 — D5의 구조 해소)

치환자(`{profile}`·`{dock}`·`{internal}`·`{name}`·`{names}` 등 실행 시 값이 결정되는 자리) **바로 뒤에
이형태 조사의 단독형을 붙이지 않는다**: 이/가 · 을/를 · 은/는 · 와/과 · 로/으로.
표시명은 사용자 지정 가능(F11)이고 게임 이름은 임의 문자열이라 **어떤 조사 선택도 언젠가 틀린다.**
받침 판정 코드를 넣는 안은 기각 — 라틴 문자·숫자·기호로 끝나는 이름에서 판정 자체가 성립하지
않고, 판정기는 "그 예외가 생기지 않는 구조"가 아니라 예외 처리의 증식이다.

허용 3형:
ⓐ **불변 조사**(에·의·도·만·까지·부터·마다 등 — 이형태가 없어 어떤 이름에도 틀리지 않는다).
ⓑ **병기형**("을(를)"류) — `{name}` 계열의 기존 관례로 **유지**하되 신규 문구에는 권장하지 않는다.
ⓒ **불변 명사 경유**("{profile} 프로필을 …" — 조사가 '프로필'에 붙는다) — **권장 정본 문형**.
괄호·홑낫표가 치환자를 격리한 자리(`「{name}」의`, `({dock}/{internal})을`)는 조사가 치환자에
붙은 것이 아니므로 대상 밖이다.

기계 판정은 §15-B ⑪. 이 절은 어휘 규칙 행이다 — 값 고정 게이트(`test_wording_10a`)의 대상이
아니며, 소관 분리는 §10-A "값 고정 게이트와의 관계" 문단의 문법을 따른다.

### 15-C. 지켜야 할 정상 동작 (HANDOFF-QA-MAINT §5 전수 승계 — 불변)

이 재편은 표시 층 재배치 + 소규모 route 확장이다. §5 전 항목(재적용 맞바꿈=G3 체크인 **그 자체는 M1 정상 동작** — §5-E는 그것을 표시할 뿐 동작 불변 · already 무쓰기 · 토큰 1회용 · 빈 슬롯 무확인 저장 · 조기 GAME_RUNNING · 2단계 복원 · `ok:true` 불변식 등)이 그대로 성립해야 하며, 위반은 구현 오류다. QA 브리핑에 §5 링크 필수.

⚠️ **8판 정오 — "already 무쓰기"의 범위(P16 E2)**: 이 항은 **복원(restore)의 `already`** 계약이다("되돌릴 내용이 이미 그것이면 아무것도 쓰지 않는다" → 그래서 화면도 재조회하지 않는다). **일괄 적용 결과행의 `already`는 다른 것이다** — 엔진은 그 경로에서도 `.applied` 그림자 사본을 갱신한다(`engine.py:626`). 두 `already`를 한 문장으로 읽으면 §5-E 관측이 "무쓰기인데 지문이 변했다"로 보여 오진한다(실제로 `.applied`를 지문에서 빼는 정오 1번이 여기서 나왔다).

### 15-D. 알려진 한계 — 구현 확인 종결분 (8판 신설)

핸드오프 §3의 "구현 시 확인할 잔여 정합 2건" 중 **ⓑ의 종결 판단**이다(ⓐ = `GAMES_EXCLUDED_NOTE`·`QAM_ABOUT_GUIDE` 조건 계약의 프로브 반영은 P15-C에서 완료). 아래 둘은 **결함이 아니라 정의가 다른 두 수를 화면이 각자 옳게 쓰는** 경우이고, 어긋남은 **registry가 손상된 병적 사례에서만** 관측된다 — P8 R2 전례 문법(사용자가 확정한 위협 모델 밖의 데이터 손상은 알려진 한계로 처분)을 적용해 **문서화로 종결한다.**

**12판**: 사실성 점검 22건 중 **미채택 3건(11·14·18)은 여기 등재하지 않는다** — 그것은 종결된 판단이 아니라 **실기 재판정 대기분**이고(§16-⑯), 같은 사안이 "종결"과 "미결"의 두 지위를 동시에 갖지 않게 한다. 실기에서 빈도가 확인되어 사용자가 종결하면 그때 E10~E12로 승격한다.
